# 02. 모듈형 디자인 도우미 프레임워크 (초안 v0.2)

> 결정 사항(사용자 확인): **모듈형** · 각 모듈을 **에이전트가 담당** · 검증은 **정성 피드백** 중심 · 레퍼런스 **4종 분류** 채택
> 상태: 초안. SNS 작업기 보강 조사(`docs/research/a*.md`) 결과를 반영해 v0.2로 업데이트할 예정

---

## 1. 설계 원칙

1. **단계를 고르는 구조다.** ①~⑧을 매번 순서대로 다 밟지 않는다. 상황(모드)에 맞는 모듈만 조합한다.
2. **각 모듈은 산출물 하나를 책임진다.** 모듈 사이에는 문서(마크다운 카드)를 주고받는다.
3. **사용자가 배우도록 돕는다.** 코치 모듈이 "다음에 무엇을, 왜 하는지"를 설명하고, 사용자가 먼저 시도하게 한 뒤 피드백한다.
4. **기록이 연료다.** 모든 결정과 실험(피드백)은 결정 로그로 남겨 다음 레퍼런스로 다시 쓴다.

## 2. 모듈(에이전트) 구성

| 모듈 | 담당 단계 | 입력 → 산출물 | 탑 디자이너 근거 |
|---|---|---|---|
| **M0 코치(오케스트레이터)** | 전체 | 사용자 상황 → 모드 선택, 단계 안내, 학습 피드백 | — |
| **M1 문제 정의** | ① | 기획서·와이어 → 문제 진술, 관찰 목록, 검증 질문 | 토스(관찰), Linear(문제 검증 우선) |
| **M2 맥락 수집** | ② | 현행 업무·기존 화면·제약 → 맥락 카드(여정, 제약, 과거 결정) | 토스(과거 실험 먼저), Airbnb(스토리보드) |
| **M3 레퍼런스 수집** | ③ | 디자인 질문 → 레퍼런스 카드(4종) | Mobbin, GoodUI, Baymard, 원칙 문서 |
| ├ M3-a SNS 작업기 리서처 | ③ | 디자이너 작업기 → 기법 카드 | 개인 블로그·SNS |
| └ M3-b 도메인 리서처 | ③ | 도메인(B2B·임상) 패턴 → 패턴 카드 | NN/g, 엔터프라이즈 디자인 시스템 |
| **M4 발산** | ④ | 문제 1개 → 대안 3~8개(극단안 포함) | Crazy 8s, 11-star, Rauno의 극단 실험 |
| **M5 수렴·크리틱** | ⑤ | 대안 → 원칙 렌즈 평가, I like / I wish / What if | 토스 PP 리뷰, HIG Hierarchy |
| **M6 구체화** | ⑥ | 선택안 → 상태·엣지케이스·인터랙션 스펙 | Linear(스크린샷 위에 디자인) |
| **M7 정성 검증** | ⑦ | 스펙·시안 → 인터뷰·UT 스크립트, 피드백 종합 | Linear(리서치·피드백), NN/g |
| **M8 학습 기록** | ⑧ | 모든 산출물 → 결정 로그(무엇을, 왜, 무엇을 버렸나) | 토스(실패 사례까지 기록) |

## 3. 모드 (모듈 조합)

| 모드 | 언제 | 조합 |
|---|---|---|
| **와이어프레임 디벨롭** | 기획서·와이어를 받았을 때 | M1 → M2 → M3 → M4 → M5 → M6 → M7 → M8 |
| **문제 해결(특정 이슈)** | "이 화면의 X가 불편하다" | M1(축약) → M3 → M4 → M5 → M8 |

## 4. 공통 데이터 형식

### 레퍼런스 카드 (M3 산출물)

```yaml
id: REF-001
type: 비주얼 | 패턴 | 근거 | 원칙        # 레퍼런스 4종
title: "Linear 이슈 목록의 다중 선택 + 일괄 액션 바"
source: <링크>
designer_or_org: Linear
problem_it_solves: "대량 행에서 선택 상태와 일괄 액션을 명확히"
applies_to: [O1, O2]                      # 프로젝트 관찰 ID
evidence: "출처의 근거(인용, 연구, 실험 결과)"
confidence: 0.0~1.0
how_to_apply: "우리 화면에서의 적용 아이디어 1~2줄"
```

### 결정 로그 (M8 산출물)

```yaml
id: DEC-001
date: YYYY-MM-DD
question: "선택 상태와 저장 상태를 어떻게 구분할까?"
options_considered: [A, B, C]
chosen: B
why: "원칙/피드백 근거"
rejected_because: {A: "...", C: "..."}
feedback_source: "약사 2명 인터뷰"
revisit_if: "다시 검토할 조건"
```

## 5. 학습 가이드 방식 (M0 코치)

각 단계는 같은 순서로 진행합니다.

1. **왜(Why)**: 탑 디자이너가 이 단계를 하는 이유를 사례 한 줄로 설명한다.
2. **해보기(Try)**: 사용자가 먼저 시도한다. 예: "O1에 대한 대안을 3개 스케치해 보세요."
3. **비교(Compare)**: 에이전트가 만든 안, 레퍼런스와 나란히 놓고 비교한다.
4. **회고(Reflect)**: 무엇이 달랐는지, 다음에 무엇을 먼저 볼지 정리하고 결정 로그에 남긴다.
