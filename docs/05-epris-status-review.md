### 2-2. HTML과 회의록 사이의 불일치 (분석 수정 필요)

1. **펜 필기가 이미 "사업범위 밖"으로 회의록에 기록되어 있다.** 회의록은 "필기 기능은 태블릿 기본 기능은 사용 가능하며, 앱에서 스타일러스 펜 그리기 입력 요구사항은 **사업범위 밖임**"이라고 적었다. HTML은 이 사안을 "점검 필요로 열려 있다"고 설명한다. HTML이 다른 버전의 회의록을 봤을 수 있다.
   - 이 기록 때문에 문제는 "전달하지 않았다"에서 **"계약 공수(펜 그리기 20 M/D)에 있는 항목을 회의 자리에서 범위 밖이라고 선언했고, 변경 합의 절차가 없다"**로 바뀐다. 오히려 더 시급하다. 고객이 동의했는지, 공수를 어떻게 조정할지가 기록되어 있지 않다.
2. **F08 인용 오류.** HTML은 10/21에 "처방 비고를 툴팁 대신 독립 컬럼으로" 요청했다고 쓴다. 회의록(v1.0)의 해당 문장은 **입원조제 투여량** 정보를 빈 컬럼에 직접 노출해 달라는 것이다("이 경우 투여량 팝업이 필요 없다고 하심"). 결론(열어야 보이는 정보는 안 본다)은 같지만 대상이 다르다.
3. **처방 비고는 설계서에 이미 독립 컬럼으로 있다**[설계서 p.5]. 또 설계서 p.4의 환자 테이블 헤더에 체크박스가 보인다. HTML의 "환자별 체크박스 없음" 판정은 개발팀 확인이 필요하다(신뢰도 0.6). 대조 결과는 `projects/epris/m2-traceability.md`에 있다.
4. **HTML의 10/21 인용 몇 개가 회의록 v1.0에 없다.** 예: "대상 기기 펜 지원 스펙 최종 점검 필요", "조제 메모·레지멘 가변 높이 대응 필요". 회의록 판본을 확인해야 한다.
5. **"긴급 시간당 300건"은 해석이 갈린다.** 회의록 원문은 "시간 단위로 모니터링하며 평균 300건 수준 발생"이다. 시간당인지 하루인지 확인해야 한다. 어느 쪽이냐에 따라 긴급 화면 설계(알림, 자동 다음, 큐)의 강도가 달라진다.

> 결론: HTML의 **근본 진단은 유지**한다. 다만 근거 인용 4곳을 고친 뒤 공유해야 한다. 사실 오류가 하나라도 있으면 상대가 분석 전체를 기각할 빌미가 된다.

## 4. 방향성 제안

### 4-1. 제품 정의: "목록이냐 처방전이냐"는 양자택일이 아니다

10/21의 "환자별로 타 약국·오더와 관계없이 전체 처방 확인" 요구는 **환자 단위 뷰**를 달라는 뜻이다. 이것이 원안의 "처방전 뷰"가 돌아올 자리다.

```
[작업 큐: 목록]  ──탭──▶  [처방전 뷰: 환자 1명]
 - 미감사 N/M, 상태 위계         - 판단 수치 고정 상단(체중·Scr/CrCl·BSA·WBC/ANC)
 - 일괄 처리는 [접수] 상태만      - 전 약국·전 오더 처방, D/C·보류 사유 인라인
 - 긴급 알림                      - 메모(키보드 필기 입력), 이전/다음 환자
                                  - 감사 저장 → 자동 다음 환자 (긴급 화면 패턴 일반화)
```

- **목록은 "어디까지 했나"를, 처방전 뷰는 "맞게 판단했나"를 맡는다.** 두 화면이 서로 다른 일을 한다.
- 긴급 화면의 목록-상세 + 자동 다음 구조[설계서 p.14]를 이미 만들었으므로, 이를 일반화하면 재사용 비용이 낮다(추론).
- 이 안은 원안의 의도(맥락·흔적·확정)를 되살리고, 기술 제약(필기감, 화면 크기)은 피한다. 대신 공수산정의 "처방전 이미지 생성 + 펜 그리기" 항목을 **이 안으로 대체한다는 합의**가 필요하다.

신뢰도 0.7. 약사가 종이에 무엇을 적는지(4-3 질문)에 따라 달라진다.

### 5-2. 프레임워크 보완점 (이번 사례에서 드러난 것)

1. **"요구사항 추적" 능력이 없다.** 이번 근본 원인은 원안에 있던 것이 조용히 사라진 것이다. M2에 **원안 ↔ 산출물 ↔ 회의록 대조 매트릭스** 절차를 추가하거나, 별도 모듈(`design-requirements-tracer`)을 만드는 것을 제안한다.
2. **범위·계약 맥락이 없다.** 디자인 결정이 공수나 범위에 영향을 주면 "PM 확인 필요"로 표시하는 규칙을 conventions에 추가한다.
3. **분석 산출물의 사실 검증 단계가 없다.** HTML처럼 강한 결론을 내는 문서는 인용 대조(verify) 단계를 거쳐야 한다. M5 또는 M1 끝에 "인용 대조 체크리스트"를 넣는다.
4. **에이전트용 프로젝트 문서가 부족하다.** 에이전트가 읽을 수 있도록 원안·회의록 원문(또는 텍스트 추출본)을 `projects/epris/sources/`에 두어야 한다. 개인정보와 실명은 제거한다.

## 6. 신뢰도와 주의사항

- **종합 신뢰도 0.75.** 근본 진단(처방전 vs 목록)은 0.8이다. 4-1 처방전 뷰 방향은 0.7로, 약사 확인이 필요하다.
- Figma 최신 시안을 보지 못했다. 설계서 v1.1(10/13) 이후의 변경 사항은 반영하지 못했다.
- 공수산정, 세부계획, 킥오프 관련 내용은 모두 HTML 인용을 그대로 옮긴 것이다. 원문으로 검증하지 않았다.
- 회의록의 "펜 사업범위 밖" 기록은 고객이 합의했는지 불분명하다. 계약 관점의 판단은 PM의 몫이다.
