# 03. 프로젝트 브리프: 전자처방검토 시스템(ePRIS) 와이어프레임 분석

> 입력: 약제부 전산 요청 기획서(와이어프레임, 23p, 2026-03 신규)
> 목적: 프레임워크 ① **문제 검증** 단계의 재료로 쓰기 위해 기획서를 구조화하고 디자인 질문을 뽑는다.
> 검증 방식: 정성 피드백(약사 인터뷰·관찰·사용성 테스트) 중심 · B2B(병원 내부) 앱

---

## 1. 기획서 구조 요약

### 1-1. 화면 흐름

```
로그인(HIS 연동)
  └▶ 접수 약국 선택  [입원조제 | 항암제조제2 | TPN조제]
       └▶ 오더 구분 선택 [정규 | 추가 | 긴급 | 전체]
            ├─ (입원조제 + 긴급) ─▶ ④ 긴급 처방전 조회 (좌: 목록 / 우: 처방전, 자동 다음)
            └─ (그 외) ─▶ 병동 선택(1동/2동, 다중) ─▶ ② 처방전 조회 (공통 필터바 + 처방 테이블)
                                                          ├ ③-1 입원조제 처방전
                                                          ├ ③-2 항암제조제2 처방전 (묶음 단위)
                                                          └ ③-3 TPN조제 처방전
```

### 1-2. 화면 구성 요소

| 영역 | 구성 |
|---|---|
| 필터 바 | 접수일·처방일(체크박스 + 기간), 오더 구분(라디오, 추가 차수 콤보, 긴급 시간대), 감사 미완료, 인수인계, 병동(다중, "41 [10]" 형식으로 표시), 환자별, 바코드 스캔, 약품 구분, 팀 구분(A~F) |
| 처방 테이블 | 2단 헤더(환자 행 + 약품 행), 약 20개 컬럼, 헤더 고정. 약국별로 컬럼 구성이 다름 |
| 숨은 정보 | 셀 모서리 삼각형 → 툴팁/팝업(용법 비교·CDSS, 약사 MEMO, 감사 시간, 블루시트, TPN 총량 등) |
| 행 상태(배경색) | 선택=초록 `#b5d5d4` · 보류/반납=분홍 `#eacccc` · 감사 저장=파랑 `#adc5d9` · 검토 저장=주황 `#fbe5d6` · 문의/HD=회색 `#afabab` |
| 액션 | [문의/HD] → [검토 저장] → [감사 저장], [저장 취소](한 단계 되돌리기). 일괄 선택은 전체/환자별/처방별(항암은 묶음별) |
| 연동 | KIMS POC(약품 정보), BESTCare 처방감사일괄확인(서명 연동), 라벨 바코드(1안: 기존 바코드를 QR로 / 2안: 신규 바코드) |

### 1-3. 기획서에 드러난 설계 의도

- **종이 처방전의 디지털 전환**이다. 페이지마다 "참고: 종이 처방전"이 붙어 있고, 컬럼 배치도 종이를 기준으로 했다. 사용자(약사)의 기존 멘탈 모델을 유지하려는 의도로 보인다.
- **처리량 중심**이다. 일괄 선택, 저장하면 다음 환자가 자동으로 열리는 흐름(긴급 화면), 바코드로 바로 찾기가 모두 이 방향이다.
- **안전과 추적성**도 중시한다. 검토자·감사자 이름과 시간을 남기고, 단계별로 저장하고, 보류·반납·D/C를 표시한다.

## 2. 디자인 관점의 관찰 (가설 수준)

> 아래는 기획서만 보고 세운 **가설**입니다. 실제 사용자(약사)의 정성 피드백으로 검증해야 합니다. 신뢰도는 "디자인 이슈일 가능성"입니다.

| # | 관찰 | 왜 중요한가 | 신뢰도 |
|---|---|---|---|
| O1 | **선택 상태와 저장 상태가 모두 행 배경색으로 표현된다.** 이미 감사 저장된(파랑) 행을 다시 선택하면 어떤 색이 보이는지 정의되어 있지 않다. | 상태 혼동은 곧 감사 누락 위험이다. 색만으로 상태를 구분하면 색각 이상, 빛 반사, 저채도 환경에 취약하다. | 0.85 |
| O2 | 상태가 6가지(기본·선택·보류·문의·검토·감사)이고 색이 모두 저채도 파스텔이다. | 한눈에 "어디까지 했나"를 파악하기 어려울 수 있다. 진행 상황 요약(예: 감사 32/40)이 없다. | 0.75 |
| O3 | **"세로(태블릿 세로 방향)"에 컬럼 20개짜리 2단 테이블**을 넣었다. | 터치 대상이 작고, 글자도 작아진다. 가로 스크롤이 생길 수 있다. 실제 기기와 사용 자세(서서, 카트 위 등)를 확인해야 한다. | 0.7 |
| O4 | 마법사(접수약국→오더구분→병동) 3단계에서 고른 값이 필터 바에 다시 나온다. | 매일 같은 조합을 쓴다면 3단계는 반복 비용이다. "내 근무 설정"이나 최근 조합을 기억하는 방식이 대안이 될 수 있다. | 0.7 |
| O5 | 중요 정보(CDSS, 용법 비교, MEMO)가 **셀 모서리의 작은 삼각형 툴팁**에 숨어 있다. | 엑셀식 관습이라 약사에게는 익숙할 수 있지만, 터치 환경에서는 발견하기도 누르기도 어렵다. 특히 CDSS 경고는 안전 정보인데 숨어 있다. | 0.8 |
| O6 | 긴급 화면만 **목록-상세 + 자동 다음** 구조다. | 큐 처리에 강한 패턴이다. 정규·추가 처방에도 "한 환자씩 처리 모드"가 필요한지 확인해 볼 만하다. | 0.6 |
| O7 | 버튼 색과 상태 색이 대응한다(검토 저장 버튼=주황 → 행도 주황). | 좋은 점이다. 버튼에서 결과를 예측할 수 있다. 이 규칙을 끝까지 일관되게 지켜야 한다. | 0.8 (강점) |
| O8 | "저장 취소"는 한 단계만 되돌린다(감사→검토→NULL). 저장 전 확인 단계는 없다. | 일괄 선택 후 감사 저장처럼 실수 비용이 큰 액션에 확인이나 실행 취소 피드백(토스트 등)이 필요한지 정해야 한다. | 0.65 |
| O9 | 약국마다 컬럼 구성이 다르고, 기획서에 "파란 글씨 = 다른 부분"으로 표시되어 있다. | 같은 위치에 다른 정보가 오면 여러 약국을 오가는 약사가 혼동할 수 있다. 공통 골격과 가변 영역을 나누는 규칙이 필요하다. | 0.7 |
| O10 | 기획서 안의 불일치가 두 곳 있다. ① 접수약국 선택지는 "TPN조제"인데 2장 설명에는 "주사조제"가 나온다. ② 검토 저장 색이 RGB `251,229,214`로 적혀 있는데, 함께 적힌 HEX는 `#afabab`(문의/HD와 같은 값)다. RGB 기준으로는 `#fbe5d6`이 맞다. | 기획 확인이 필요하다. 개발 단계에서 그대로 옮기면 상태 색이 겹칠 수 있다. | 0.9 (사실) |

## 3. 문제 진술 초안 (① 문제 검증의 출발점)

> **"약사는 [근무 중 할당된 병동의 처방]을 [빠르게] 그러면서도 [누락·오류 없이] 검토·감사하고, [어디까지 했는지]를 언제든 알 수 있어야 한다."**

이 진술은 확인이 필요합니다. 아래 질문을 약사 1~3명에게 물어보면 됩니다.

1. 하루(근무)에 처리하는 처방 건수와 가장 바쁜 시간대는 언제인가요? → **처리량** 기준
2. 종이 처방전에서 가장 자주 실수하거나 놓치는 것은 무엇인가요? → **안전** 우선순위
3. 처방 하나를 감사할 때 실제로 **눈이 먼저 가는 컬럼** 3개는 무엇인가요? → 정보 위계(Hierarchy)
4. 근무 중 태블릿을 어떻게 들고 쓰나요? (거치, 손에 듦, 서서/앉아서) → O3
5. 인수인계할 때 무엇을 넘기나요? → 진행 상황 표시(O2)

## 4. 이 프로젝트에 맞춘 프로세스 모드

정성 피드백 중심의 B2B 프로젝트이므로 `docs/02-framework-modular.md`의 **"와이어프레임 디벨롭 모드"**를 기본으로 씁니다.

```
① 문제 검증(위 질문 5개) → ② 맥락(종이 처방전·HIS·BESTCare) → ③ 레퍼런스(B2B 테이블·임상 UI·상태 표현)
→ ④ 발산(O1·O3·O5 각각 3~8안) → ⑤ 수렴(원칙 렌즈 + 약사 피드백) → ⑥ 상태·엣지케이스 스펙 → ⑦ 정성 검증 → ⑧ 결정 로그
```
