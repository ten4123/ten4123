# A2. 국내 디자이너 1인칭 작업기 리서치 (SNS/블로그/테크블로그)

- 작성: SNS 작업기 리서처 (국내) 모듈
- 조사일: 2026-10-23
- 방법: WebSearch만 사용함. 페이지를 직접 열어 읽는 것(WebFetch/curl)은 막혀 있었음. 그래서 모든 인용은 **검색 결과 스니펫에 실린 문장**이고, 본문 전체를 읽고 확인한 것이 아님. 인용문은 원문의 일부일 수 있음.
- 신뢰도 기준: 0.8 이상은 원문 제목·URL·핵심 문장이 스니펫에서 확인됨. 0.6~0.7은 요지만 확인되고 세부는 확인하지 못함. 0.5 이하는 간접 자료(인터뷰나 요약)임.

---

## 1. 요약 — 공통 패턴

- **원칙이 수렴 기준 역할을 함.** 토스 작업기는 사내 제품 원칙을 근거로 시안을 고르고 버림. 예: Easy to answer는 "모든 질문은 3초 안에 대답할 수 있는가", 그 밖에 Value first/Cost later, One thing per page가 있음. 문제를 정의하는 문장 자체가 "원칙 위배"로 쓰이는 경우가 많음.
- **"뾰족한 가설 1개 → 실험"이 발산보다 앞섬.** 토스와 당근 모두 여러 시안을 펼치는 과정보다 가설을 선명하게 만드는 과정을 강조함. 예: "한 번에 하나만 검증", "하나의 가설로 극한의 성과를", "1일 1실험". 시안 비교는 주로 A/B 테스트나 현장 UT로 결정함.
- **레퍼런스는 경계 대상으로 다뤄짐.** 「독이 되는 레퍼런스 활용법」(토스)은 남의 화면을 참고할수록 기능이 늘어 핵심 정보가 묻힌 사례를 다룸. 브런치 글들도 "표면 UI를 복제하지 말고 판단 기준을 배우라"고 함. Mobbin이나 Pinterest를 쓰는 법을 1인칭으로 쓴 작업기는 찾지 못했음(→ 공백).
- **정성 검증은 "현장에서 직접 만나기"가 기본임.** 사례로 점심시간 사용자 인터뷰(토스), 카페 게릴라 테스트에서 시안 3개 비교(토스플레이스), 본사 초대 대면 인터뷰(당근), 직접 배달해 보고 POS 촬영하기(LINE 데마에칸), 6개 시나리오 FGT/FGI(LY)가 있음.
- **사내 테스트를 믿지 않음.** 동료 대상 프로토타입 테스트는 통과했는데 출시 후 사용이 적었던 사례(달력)가 있음. "내 아이디어를 너무 믿지 마세요"라는 반성이 반복해서 나옴.
- **정성이 정량을 이길 때가 있음.** 차이가 근소하면 "전환율이 낮은 안이라도 더 나은 정성적 경험을 주는 안"을 채택한다는 사례가 있음(토스 가입).
- **움직임이나 촉감이 핵심이면 정적 시안을 건너뜀.** 디자이너가 AI와 함께 SwiftUI 앱을 직접 만들어 시안이자 스펙으로 넘긴 사례가 있음(토스). 이 경우 "구체화" 단계가 코드 프로토타입으로 바뀜.
- **가이드라인을 먼저 만들지 말라.** 회고형 교훈임. "여러 방향으로 그려보고 빨리 제품에 적용 → 최소 10가지 학습 후 가이드라인"(토스 첫 그래픽 디자이너).

### 카드 1. 이지윤 / 토스 — 내 문서함 전면 개편
- 글: [크고 복잡한 제품, 과감하게 갈아엎기](https://toss.tech/article/mydoc) (2023.9, Simplicity23 세션과 연계) / 같은 필자의 시리즈 [달리는 기차의 바퀴 교체하기 1. Planning](https://toss.tech/article/restructuring-planning), [2. Restructuring](https://toss.tech/article/restructuring)
- 핵심 작업 방식
  - 문제 정의: 조직 단위로 서비스를 한 화면에 묶었더니 복잡도가 커졌다고 진단함. "유저들이 들어와서도 내 문서함을 이해하지 못했어요"
  - 화면 배치나 문구를 다듬는 수준에서 멈추지 않고, 사용자 행동과 가치 기준으로 제품을 쪼갬(발급하기 / 납부하기 / 알림 받기).
  - 과감하게 뺌: 한 번 신청하면 안내만 받으면 되는 서비스는 고정 진입점을 없애고 알림 탭으로만 받게 함.
  - 새 개념과 네이밍을 찾고 팀을 설득하는 데 "약 2달"이 걸림.
- 단계: ①②④⑤⑥
- 레퍼런스 태그: [원칙](Simplicity) [근거](사용자 이해 실패)
- 신뢰도: 0.85

### 카드 2. 토스 디자이너 — 보험금 청구 "Easy to answer"

- 핵심 작업 방식

  - 원칙을 체크리스트로 씀: "과업 완료까지의 모든 질문은 3초 안에 대답할 수 있는 것들인가?"
  - 질문을 바꿈: "전문가 도움받을까요, 직접 할래요?"를 "서류 있나요?"로 → "이탈하는 사용자가 50% 감소"(다른 글에서는 60%로 언급됨). 보험사 목록도 가입한 곳만 보여 줌.
- 단계: ①⑤⑥⑦(정량)
- 레퍼런스 태그: [원칙] [근거]
- 신뢰도: 0.85

### 카드 4. 토스 디자이너 — 회원가입 개선 (반복 실험 회고)
- 글: [완성 없는 이야기, 가입 과정 개선](https://toss.tech/article/signup) / 관련: [거꾸로 입력하는 가입 화면, 처음에 어떻게 떠올렸을까?](https://toss.tech/article/toss-signup-process)
- 핵심 작업 방식
  - 인트로를 없애고 이름부터 묻는 실험을 함 → "가입 전환율은 거의 차이가 없었어요" (실패도 기록함)
  - 다른 팀 UT에서 시니어가 주민번호 입력을 꺼린다는 점을 확인함 → 생년월일로 바꾼 안을 프로토타입으로 만들어 토스 미사용 시니어 대상으로 다시 UT함.
  - UT에서 OS별 차이를 발견함: iOS는 편하다는 반응이었고 "Android 사용자들은 이름을 적는 것조차 민감한 반응"을 보임.
  - 의사결정: 차이가 근소하면 "보다 더 나은 정성적인 경험을 줄 수 있는 안이 채택될 때도"
  - 원칙 충돌: 필드를 모두 노출하면 "1 thing for 1 page" 원칙과 부딪혀서 네 페이지로 나누는 안도 검토함.
- 단계: ①②④⑤⑥⑦⑧

## 4. 공백 / 한계

- **본문 미열람**: 모든 내용이 검색 스니펫과 요약에 기반함. 인용문이 원문과 미세하게 다를 수 있고, before/after 이미지나 시안 개수 같은 세부는 대부분 확인하지 못했음. 일부 수치는 같은 사례 안에서도 다르게 나옴(보험 이탈 감소 50% vs 60%).
- **토스 편중**: 22개 카드 중 15개가 toss.tech임. 토스는 검색에 잘 걸리고 1인칭 작업기도 많지만, 결과적으로 "원칙 기반 수렴과 A/B" 관점에 치우쳐 있음.
- **찾지 못한 영역**
  - Mobbin, Pinterest, 자체 아카이브 같은 **레퍼런스 수집 루틴을 1인칭으로 쓴 작업기**는 찾지 못함. 사이트 모음 글(velog, medium)만 있었음.
  - **발산(여러 대안 펼치기)** 과정을 구체적으로 보여 주는 글이 드묾. 시안 3개 비교(토스플레이스)와 4페이지 분할안 검토(토스 가입) 정도뿐임.
  - **와이어프레임이나 기획서를 디자인으로 발전시킨** 단계별 작업기는 거의 찾지 못함.
  - **디자인 크리틱 운영기(국내)**: 한국어 1인칭 글은 찾지 못함. 영문(HashiCorp) 자료만 나옴.
  - 카카오, 네이버, 오늘의집, 29CM, 뱅크샐러드: 디자이너가 쓴 1인칭 작업기는 검색되지 않음. 채용 공고, 인터뷰, 외부 분석 기사만 나옴.
  - LinkedIn 포스트, 유튜브 컨퍼런스 영상(Simplicity 세션)은 내용 단위로 확인하지 못함. 세션이 존재한다는 것만 확인함([Simplicity24 소개](https://designcompass.org/2024/11/06/toss-simplicity24/), [Simplicity23](https://toss.tech/article/simplicity23)).
- **형식 한계**: 당근 자료는 인터뷰 형식(채용 블로그)이라 본인이 쓴 작업기보다 신뢰도를 낮게 매김. 배민 자료는 조직 활동기임.
- **다음 조사 제안**: 페이지를 직접 열 수 있는 환경에서 toss.tech/category/design 전체 목록을 확인할 것. Simplicity23/24 세션 스크립트, 당근 `medium.com/daangn` 디자인 태그, 브런치 '프로덕트 디자이너' 키워드 상위 작가, 디스콰이엇·LinkedIn의 "작업기" 포스트도 보강할 것.
